## Question

The harness ships a skills catalog at `skills/catalog.md`, regenerated by
`skills/generate-catalog.sh` through `piw generate-catalog`. The intent is to
tell the agent which low-frequency skills exist, without loading every skill
into context.

Found while resolving **CLI surface**. Four problems, and none of them is about
where the command lives.

## Findings

1. **Nothing consumes the catalog.** A search across the repository finds no
   reference to `skills/catalog.md` outside the generator and the catalog
   itself. Neither the workflow skill nor `APPEND_SYSTEM.md` mentions it. The
   mechanism is generated but not wired.

2. **The committed catalog is the signature of a broken run.** Every
   description is empty:

   ```
   - **`browser-tools`** —  *(user-invoked)*
   ```

   Regenerating it on a host with python3 and PyYAML fills them in. So the
   committed file came from an environment where the YAML extraction failed,
   and the failure is silent: the helper ends with `2>/dev/null || echo ""`.

3. **The generator misses active skills.** It scans `skills/system/` and the
   promoted vendor buckets, which default to `engineering` and `productivity`.
   It therefore omits:

   - `skills/vendor/mattpocock/skills/misc/`, four skills that pi does load.
   - `skills/variant/`, a top-level skills directory.

   The `in-progress` and `deprecated` omissions are correct.

4. **It needs python3 and PyYAML on the host.** `piw generate-catalog` runs the
   script on the host, not in the container, and the extraction is a
   `python3 -c` call. This contradicts the standing preference that piw runs on
   a host without python3, jq, or yq.

## What the catalog is for

The first reading of this ticket was wrong, and the correction is worth
recording because the goal is not written down anywhere. It belongs in the docs.
See #30.

pi's mechanism is that `docs/skills.md` adds each skill's name, description, and
path to the system prompt, and the system prompt is sent on **every turn**. The
catalog's purpose is the opposite: one artifact, read **once**, describing
**many** skills. The index then lives in the conversation and is periodically
refreshed, instead of being repeated in the system prompt forever.

### The tension it creates

**pi has no setting that suppresses skill advertising.** `settings.md` offers
only `skills`, which chooses the paths, and `enableSkillCommands`, which chooses
whether `/skill:name` commands are registered. A skill is advertised if pi
discovers it, so the only way to keep it out of the system prompt is to keep it
out of pi's discovery paths.

Measured: the harness holds 43 skills, and their `name` and `description` lines
total 6967 bytes, roughly 1741 tokens. That is the per-turn cost of letting pi
advertise them.

So the catalog only saves tokens if the harness's skills stop being discoverable
by pi, and the catalog becomes the index instead. That is a real trade. The
agent loses pi's progressive disclosure and its `/skill:name` commands, and
gains a smaller system prompt.

That trade is the question this ticket now has to answer.

## Questions

- Is the catalog consumed at all, or is it documentation for humans?
- If it is consumed, by what? A skill the agent reads on demand, a line in
  `APPEND_SYSTEM.md`, or pi's own skill discovery?
- Where does the generator run, and in what language, given that the host has
  no python3 guarantee?
- Which buckets are promoted, and does `misc` belong in the catalog?
- Does the catalog survive at all, or does pi's own skill listing make it
  redundant?
