## Question

The harness ships a skills catalog at `skills/catalog.md`, regenerated by
`skills/generate-catalog.sh` through `piw generate-catalog`. The intent is to
tell the agent which low-frequency skills exist, without loading every skill
into context.

Found while resolving **CLI surface**.

## What the catalog is for

pi's mechanism adds each skill's name, description, and path to the system
prompt, and the system prompt is sent on **every turn**. The catalog's purpose
is the opposite: one artifact, read **once**, describing **many** skills, so the
index lives in the conversation and is periodically refreshed instead of being
repeated forever.

That goal was not written down anywhere, which is why the first reading of this
ticket went wrong. It belongs in the docs. See #30.

## Answer

### The mechanism exists, and the harness already uses it

`disable-model-invocation: true` in a `SKILL.md` frontmatter removes the skill
from the system prompt entirely, while pi keeps it loaded and `/skill:name`
keeps working. `dist/core/skills.js:276`:

```js
const visibleSkills = skills.filter((s) => !s.disableModelInvocation);
```

It is tested rather than incidental. The test suite contains
`should exclude skills with disableModelInvocation from prompt` and
`should return empty string when all skills have disableModelInvocation`. The
original request, issue #927, asked to "elide the skill name and description
from the harness system prompt", and the implementing commit says the skill is
"hidden from the system prompt, preventing agentic invocation. Users can still
invoke explicitly via `/skill:name`."

The harness already hides 21 of its 43 skills:

| | Skills | Bytes | Per turn |
|---|---|---|---|
| Shown | 22 | 3835 | roughly 958 tokens, every turn |
| Hidden | 21 | 3132 | nothing |

Verified against a live system prompt: all 22 shown skills appear, all 21 hidden
ones are absent, exactly.

**There is no other mechanism.** No setting, no frontmatter field, no directory
convention, no mode. `enableSkillCommands: false` does not touch the system
prompt, only interactive autocomplete. `--no-skills` disables discovery for the
whole run and kills the commands with it. Directory-based hiding, ignore files
included, removes the skill from pi entirely.

### The catalog's job

It is the model's index of the skills the model cannot see. That is exactly what
its `(user-invoked)` marker already records. What is missing is that nothing
points the agent at it, and the generator is broken.

### Final decisions

**The catalog lists only the hidden skills.** The 22 shown skills are already in
the system prompt at every turn, so listing them again is duplication. The
catalog becomes a short, stable list of "skills you cannot see, and the path to
each", which is the gap it exists to fill.

**The workflow skill points at it.** One line naming the path, and saying to
re-read it after compaction, because compaction can summarise it away. The
workflow skill is the right home: it carries harness behaviour, it is read
first, and **Environment description for the agent** is already leaning that
way.

**The current shown and hidden split stays.** Hiding a skill the model genuinely
needs to auto-select is a worse failure than paying for one it does not, and the
split is currently the vendor bundle's choice rather than ours. Revisit it as a
separate question once the catalog works.

**The generator runs in the container.** It currently runs on the host and
extracts frontmatter with `python3 -c`, which contradicts the standing
preference that the host has no python3. Running it in the container also
matches the rule that piw never executes tooling on the host.

**The generator fails loudly.** Its helper ends with `2>/dev/null || echo ""`,
which is why the committed catalog has empty descriptions. A silent empty
description is worse than a failed run.

### Findings

1. **pi's documentation got worse on 2026-09-22.** Commit `25cc5c7` replaced
   "When `true`, skill is hidden from system prompt. Users must use
   `/skill:name`." with "Hide the skill from automatic model selection". The
   behaviour did not change. The new wording describes a consequence rather than
   the mechanism, and it is why this ticket was misread twice.
2. **pi's docs wrongly attribute the field to the Agent Skills specification.**
   The specification defines `name`, `description`, `license`, `compatibility`,
   `metadata`, and `allowed-tools`. It does not define this field. Standardising
   it was proposed in issue #236 and the discussion was locked in March 2026
   without adoption.
3. **Three fields are emitted per skill**: `name`, `description`, and
   `location`. No truncation and no token budget. The only limits are validation
   warnings at 64 and 1024 characters, and an over-length value still loads.
4. **The skills section is omitted entirely** when neither `read` nor `bash` is
   a tool.
5. **The generator misses active skills.** It scans `skills/system/` and the
   promoted vendor buckets, which default to `engineering` and `productivity`,
   so it omits `skills/vendor/mattpocock/skills/misc/` and `skills/variant/`.
6. **`pi list` does not install anything**, because listing does not resolve.
   Unrelated to this ticket, but found in the same session.

### For the record, on peers

Claude Code, Cursor, and VS Code support `disable-model-invocation`. Claude Code
and VS Code also add `user-invocable` for the opposite direction. Codex uses
`policy.allow_implicit_invocation: false` in `agents/openai.yaml` rather than
frontmatter. OpenCode, Amp, and Gemini CLI do not document an equivalent.

### Open at implementation

The base image has `python3` from apt, but **PyYAML does not come with it**, and
the generator needs it. Either `python3-yaml` joins the apt list in #23's
Dockerfile, or the frontmatter parse is rewritten. `uv` is baked and could run a
script with a dependency, at the cost of a first-run download. This is a detail
for implementation, not a decision this ticket has to make.

## Consequences

- **#30 must document two things**: the catalog's purpose, and the hiding
  mechanism, including that pi's own docs describe it misleadingly.
- **#34 gains its answer for skills**: the workflow skill is where harness
  behaviour is stated.
- **The generator needs the container seam**, which means the `_in_container`
  helper gains a caller outside the tool and pi paths.
- **#29 gains a test target**: the generator should fail loudly, and a test can
  assert that it does.
