## Question

How does the `documentation` skill handle projects with existing documentation, history, layers of accumulated cruft, and legacy conventions? Migrations take years, split-brain pain is inevitable, and some docs may be non-digital (paper, physical artifacts) or already public with URLs that cannot change. Design a realistic strategy for gradual adoption: inventory, assessment, migration planning, and ongoing alignment. How does the skill coexist with legacy docs during the migration period? How does it handle docs that cannot be moved (public URLs, paper archives, third-party-hosted content)? How does the skill prevent the migration from making documentation *worse* during the transition?
